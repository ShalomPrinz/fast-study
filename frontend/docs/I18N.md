# Internationalisation and RTL

The UI ships in Hebrew and English. Hebrew is the default and the right-to-left case; English is the
source locale, so an untranslated build still reads as the code does.

## The two kinds of text

The single rule that decides everything below:

- **UI chrome is translated.** Buttons, labels, titles, placeholders, toasts, modal copy, error
  wording this app authors itself.
- **Data is never translated.** Course, lecture, recitation and material names are what is on disk.
  They render verbatim, in whatever language the user named them, under `dir="auto"` so each one
  lays itself out by its own first strong character rather than by the page's direction. That is why
  around ten `dir="auto"` attributes sit on name-rendering elements and nowhere else.

Error prose returned by `backend/`, `database/` and `downloader/` (`result.message`, `last_error`,
an extractor's `st.message`) is data by this rule: it displays in English inside translated wrappers.
Fixing that needs an error-code protocol across the services, which does not exist.

## Runtime — `services/i18n.ts`

`LOCALES` is `['he', 'en']`. `resolveLocale(stored, browserLanguage)` is pure and decides the locale:
a stored choice wins, then anything the browser reports that does not start with `en` means Hebrew.
`initialLocale()` reads `localStorage['fast-study:locale']` and `navigator.language` and hands the
answer to `activateLocale`, which loads the catalog, activates it and sets
`document.documentElement.lang` and `.dir`. That `dir` write is the single switch that flips the
whole layout.

Only an explicit pick is stored, and `chooseLocale` — activation plus the write — is what the
switcher calls. Persisting the boot-time guess instead would stamp `he` on the first visit from a
Hebrew browser and then ignore that browser forever, since a stored choice outranks it.
Both storage calls are wrapped: access throws with cookies blocked, and a lost preference must not
cost a render.

`main.tsx` awaits `activateLocale(initialLocale())` before the first render, so no component ever
runs without an active catalog — Lingui throws if one does. It falls back to English if that throws,
because an unhandled rejection there skips `render` entirely and leaves a blank page — `ErrorBoundary`
can only report a crash once something is mounted. `src/test-setup.ts` activates English for the same
reason under Vitest.

The switcher is `shared/sidebar/LanguageSwitcher.tsx`, in the sidebar footer. Its labels are endonyms
(`עברית`, `English`) and are deliberately never translated — a language is always offered in its own
script. Only its `aria-label` is.

## Adding a string

Wrap it in the Lingui macro, importing from `@lingui/core/macro` (`t`, `plural`, `msg`) or
`@lingui/react/macro` (`Trans`, `Plural`, `useLingui`). There is no `@lingui/macro` package.

- In JSX: `<Trans>Run Remaining</Trans>`, or `<Plural value={n} one="# result" other="# results" />`.
- In an attribute or an expression: `const { t } = useLingui()`, then ``t`Search` ``.
- Outside a component (a util, a service, a context callback): `import { t } from '@lingui/core/macro'`
  and use it the same way. It resolves against the globally active catalog.
- In a module-level table — `constants/pipeline.ts`, `constants/overview.ts`,
  `RecordingRow`'s `RESOLVED_LABEL` — use ``msg`…` ``, which yields a `MessageDescriptor` rather than
  a string. Those tables are built once at import time, before any locale exists; the rendering site
  resolves them with `t(descriptor)`.

Two habits keep translations honest:

- **Never splice a translated fragment into another message.** Two whole sentences beat one sentence
  with a hole in it, because the hole's grammar changes with what fills it. `notFound.ts` carries a
  lecture message and a recitation message rather than interpolating the noun; `materialIndicator.ts`
  spells out the named-material and counted-material cases separately.
- **Count anything with `plural`/`<Plural>`, never with `n === 1 ? … : …`.** Hebrew has `one`, `two`
  and `other`, and CLDR has revised that set before — `services/resolveLocale.test.ts` asserts
  against `Intl.PluralRules` rather than a fixed list.

## The extract/compile loop

```bash
npm run extract   # scan src/, update src/locales/{he,en}/messages.po
npm run compile   # only for a build outside Vite; the vite plugin compiles .po on the fly
```

`npm run extract` prints a per-locale missing count. **Zero missing for both locales is the
definition of done** — run it after every batch of new strings. Hebrew translations go in
`src/locales/he/messages.po`; the `en` catalog is filled from the source strings automatically.

A translation may carry more plural categories than the English source had. Several counts are a
bare `other` in English but `one`/`two`/`other` in Hebrew, and that is correct, not drift.

## Adding a locale

1. Add it to `locales` in `lingui.config.ts` and to `LOCALES` in `services/i18n.ts`.
2. Add its catalog to the `CATALOGS` map in the same file — a literal entry, not a templated dynamic
   import, so the bundler can see it.
3. If it is right-to-left, extend the `dir` decision in `activateLocale`.
4. Add its endonym to `LABELS` in `LanguageSwitcher.tsx`.
5. `npm run extract`, then translate.

## RTL — logical properties only

Every direction-sensitive declaration in `src/**/*.css` is logical: `margin-inline-start`, not
`margin-left`; `inset-inline-end`, not `right`; `text-align: start`, not `left`; `padding-block`/
`padding-inline` for shorthands. Direction then follows `document.dir` with no per-locale stylesheet
and no `[dir="rtl"]` overrides anywhere.

The traps a `margin-left` grep misses, and which are therefore worth checking by eye: asymmetric
four-value shorthands (`padding: 18px 12px 14px 16px`), `translateX`, individual corner radii,
`box-shadow` x-offsets, and `row-reverse`.

The one intentional exception is `ErrorBoundary.css`, which pins `direction: ltr` on the crash
report — a stack trace is LTR content whatever the UI language is.

## RTL — direction-sensitive glyphs

CSS is only half of it: a glyph that points somewhere has to flip too, and no logical property
reaches text content. Two cases exist. Copy that names a direction is translated as copy — `← Back`
is `→ חזרה` in the catalog. A glyph rendered from state goes through `shared/components/Chevron.tsx`,
which reads the active locale through `useLingui` (not `document.dir`, so a locale switch re-renders
it) and picks `◂` or `▸`. `isRtl` in `services/i18n.ts` is the single place that decides, and
`activateLocale`'s `dir` comes from it too.

`⭳` and `▾` point down, so they are the same in both directions.

Third-party CSS is the gap this leaves. `react-toastify` ships its own physical stylesheet, and its
`rtl` prop only mirrors a toast's internals — the container corner does not move — so `Layout.tsx`
picks `top-left`/`top-right` from `isRtl` itself, keeping the stack clear of the sidebar.

## Names on disk are language-agnostic

`features/lectures/utils/nextName.ts` suggests the next lecture/recitation name, and that suggestion
becomes a directory name under `DATA_ROOT`. It therefore infers the prefix from the course's own
children — `/^(.+?)\s+(\d+)(?:\.(\d+))?$/` — instead of matching the word `Lecture`. A course holding
`הרצאה 3` suggests `הרצאה 4`; one holding `Lecture 7` suggests `Lecture 8`. Only a course with
nothing to copy falls back to a translated default in the active UI locale.

The storage layer was already language-agnostic (`database/fs/paths.py` reserves only `Recitations`),
so this parser was the last place the English wording was load-bearing.

`features/downloads/utils/nameFromTitle.ts` follows the same rule for a title that already carries a
number: `sessionPrefix` hands it the course's own prefix, and only a course with nothing to copy
falls back to a translated `Lecture` / `Recitation`.

One divergence remains: `downloader/extension/regular/popup.js` mirrors `suggestName` with its own
English-only regex. It is out of scope here — non-English courses were never supported there, and
English ones still get identical suggestions.
