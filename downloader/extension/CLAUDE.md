## How it works

- **Server discovery** (`bridge.js`, popup open): `chrome.runtime.sendNativeMessage('com.faststudy.bridge', {})`. A `{port, secret}` reply means `http://127.0.0.1:<port>` with `X-FastStudy-Secret` on every server call; `{running: false}` shows "Open the FastStudy app" and calls nothing; no host registered (dev, WSL) falls back to `http://localhost:3052` with no secret. The host and its registration are `electron/`'s.
- **Self-update**: a reply's `extensionVersion` that differs from the manifest's triggers `chrome.runtime.reload()`, from the popup and from the worker's `onStartup`, at most once per shipped version (`reloadedFor` in storage), so a folder the app never refreshes cannot reload on every open.
- **Capture** (`background.js`): every request whose URL path ends in `.mp4`, `.m3u8` or `.panobf2` (Panopto's renamed HLS playlists; its `.panobf1` segments are never captured) is stored as `{url, headers, capturedAt, pageUrl}`, `pageUrl` being its tab's URL (no tab URL, no capture). The store is one ring of 50 across all tabs, deduped by `url`; the badge is set per tab and counts only that page's captures, but a page with any playlist (`.m3u8`/`.panobf2`) reads 1 (a player loads one playlist per variant, and the worker can't tell fMP4 segment `.mp4`s from real videos; the popup counts exactly).
- **Source** (popup, on open): clears the tab's badge and shows exactly one source — a YouTube page (`/download-youtube`), else this page's captures (`/download` with the raw URL + captured headers). When they include a playlist (`.m3u8`/`.panobf2`), the popup sends them (newest 30) to `POST /hls-streams` and lists only the returned streams, best first with `streams[0]` preselected, labelled `[size · duration · no audio]` (the marker only when `hasAudio === false`) and the last two path segments, plus its `.mp4` captures minus the fMP4 segments the server names in `segments` (it receives the newest 100 `.mp4`s in the same `captures` array; an old server omits `segments`, read as none; a page with only `.mp4`s makes no `/hls-streams` call, and size probes run only for the `.mp4`s shown); no stream with every failed playlist refused (`HTTP 401`/`HTTP 403`) means the page's session expired ("reload the page" headline), any other failure shows the generic streams headline; the first `detail` shows beneath either, else a `.pdf` tab (`/upload-pdf`).
- **Per-page isolation** is by exact `pageUrl === activeTab.url` (query and hash included), so captures from other tabs never leak in and navigating away hides earlier ones.
- **Sizes** of `.mp4` captures come from the server's `POST /probe-size` (an HLS stream's from `/hls-streams`' `estimatedBytes`), since `Cookie` is a forbidden `fetch` header; `[…]` while pending, `[?]` when unknown.
- **PDF**: the popup sends one `downloadPdf` message and the worker fetches the tab's PDF with `credentials: 'include'` (the user's session cookies authenticate) and uploads the bytes to `/upload-pdf`, so closing the popup never drops it. The worker keeps one `chrome.storage.session` entry per URL (`pdf:<url>`: `state` downloading/uploading/done/failed, `bytes`/`total`, `headline` message key + `params`, server `detail` verbatim); the popup renders it on open and follows `storage.onChanged`, and its open also pings the worker (`wake`). A new download of the same URL aborts and replaces the old. An entry still downloading/uploading when a worker starts fresh becomes `failed` with `errPdfInterrupted`. While the popup is closed a settled job puts ✓ (green) or ! (red) on that tab's badge, replacing the capture count until the popup opens and clears it.
- **Received file** (right-click menu): a link menu item "Send to FastStudy" (`contextMenus`, no install warning) registered in `onInstalled`, scoped by the hardcoded `targetUrlPatterns` to links containing one of the 13 material extensions (`FILE_TYPES`, upper and lower case, query included) or Moodle `mod/resource/view.php`. `FILE_TYPES` is a copy of `backend/pipeline/material_types.py` and of the server's `FILE_TYPES` in `routes/pdf.js`: change all three together. A click calls `chrome.action.openPopup` at once and the worker resolves the link: `fetch` with `credentials: 'include'` (`view.php` gets `redirect=1`), headers read then the body cancelled; name from `Content-Disposition` else the final URL's last segment. If `openPopup` fails (window unfocused, Chrome < 127) the tab's badge shows ↓ (accent) until the popup opens or the capture count replaces it; a tab-view popup already open reloads onto the received view when a new `resolving` entry appears. An HTML response, a non-2xx status, an unreachable link or an unsupported type is a red notice (`rejected`) and Download stays disabled. The one entry `received` in `storage.session` has states `resolving`, `ready`, then the PDF job's `downloading`/`uploading`/`done`/`failed`; no bytes are held while the user picks a destination, and Download (`downloadFile` message) refetches in full and posts to `/upload-file?filename=<name>` (General mode ignores the file-name field and keeps the original name). While `received` exists the popup shows only it, in place of the tab's source: the resolved file name in a read-only box where the video link sits, the green "File received (TYPE)" or red notice directly above it. It stays across popup closes until sent or replaced by the next click (a send in flight is never replaced); once a settled result or a red notice has been shown the popup marks it `seen`, and the next open drops it and shows the tab again. Lecture defaults to `latest`.
- **Lectures-only course**: a listed course's `lectures_only` flag, or for a typed-in course the server's `GET /course-structure` being `lectures_all` (fetched once per open; a failure keeps the choice), hides the kind choice and sends `kind=lecture` — except a name already among its recitations, which keeps `recitation`. Re-evaluated on every course edit.
- **Mode** (`popupMode` in storage): "App lecture" sends course/kind/name; "General video" sends `dest:'folder'` + a file name prefilled from the tab title, and shows the server's folder read-only. "Choose folder…" asks the server to have the app window open its picker (the popup can't host one); the new folder shows on the next open ([DOWNLOAD.md](../server/docs/DOWNLOAD.md)).

## MV3 rules this relies on

- Non-blocking `webRequest` with `extraHeaders` is allowed in MV3 (only `webRequestBlocking` is policy-only); `extraHeaders` is what exposes `Cookie`/`Referer`/`Origin` for the server's header replay.
- The listener is registered synchronously at top level, so Chrome re-wakes a suspended worker for it; all state is in `chrome.storage.local`. Captures are written through one promise chain so a burst can't lose an entry to a racing read-modify-write.
- The worker's download jobs write its `storage.session` entry once a second from a timer for as long as it runs: each extension API call resets Chrome's 30 s idle timer, and the write is the progress the popup shows. A killed worker loses the job (no resume); the next start marks it interrupted (a stale `received` `resolving` becomes `rejected`, red and shown once; every other active state becomes `failed`).
- The `<all_urls>` host permission exempts the popup's and worker's `fetch`es from CORS (server calls and the PDF fetch alike): measured, a POST with `X-FastStudy-Secret` to a server sending no CORS headers succeeds with no preflight. The server's allowlisted extension origin is only a backstop.

## Conventions

- No dependencies and no build step (MV3); plain classic scripts.
- Language follows Chrome's UI language (`chrome.i18n`), not the app's setting: `<html dir>` from `@@bidi_dir`, `lang` from `@@ui_locale`; static strings fill from `data-i18n` / `data-i18n-placeholder` at load. No user-facing literal in `popup.html`/`popup.js`; CSS uses logical properties only.
- A server failure shows a translated headline with the server's `error` prose verbatim beneath, never translated.
- Light theme only; `popup.css` copies the tokens it uses from `frontend/src/styles/tokens.css` and the `.btn--primary` rules from `button.css`.
- `suggestName` in `popup.js` is a port of `frontend/src/features/lectures/utils/nextName.ts` (prefix inferred from the course's own names; `next` for a video, `latest` for a PDF; a lectures-only course takes the number over lectures + recitations, a recitation after a lecture on the same number, and the prefix from its lectures). The fallback prefix comes from `_locales` (`dirLecture`/`dirRecitation`). Change both together.
- A brand-new course needs nothing here: the server creates it before the job starts.

## Testing

No suite. Load it into a Playwright persistent Chromium context (`--load-extension`, `--disable-extensions-except`, `--headless=new`) against a local server. Playwright can't attach to the toolbar popup, so open `popup.html` as a tab created with `active: false` in the lecture tab's window — its "active tab" is then still the lecture page. Chromium reads native hosts from `<user-data-dir>/NativeMessagingHosts/com.faststudy.bridge.json`, so a fake host there (any executable speaking the 4-byte length framing) drives the bridge paths. Headless Chromium never fires `onStartup` and doesn't bring a command-line extension back after `chrome.runtime.reload()`; call the handler from `sw.evaluate` instead.

A native context menu can't be driven in headless Chromium. Call `chrome.contextMenus.onClicked.dispatch({menuItemId:'send-file', linkUrl}, tab)` from `sw.evaluate`, and test the menu scope with Chrome's own matcher: add a `webRequest.onBeforeRequest` listener filtered by `LINK_PATTERNS` and `fetch` each URL.
